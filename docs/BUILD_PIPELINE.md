# Связанная сборка медиа и репостов

`node build-media.js <id>` готовит все входы публикации одним локальным процессом. Без ID выбираются только `pending` и `approved`. Начатые и опубликованные материалы автоматически не пересобираются. Сборка не меняет `content/queue.json`, статусы и даты.

Существующие команды `node render.js <id>` и `node render-reels.js <id>` передают полноценную сборку этому же процессу. Режимы `render.js --pin`, `render.js --no-video` и `render-reels.js <id> --frame` остаются отдельными экспортами для просмотра; сами по себе они не означают готовность к отправке.

## Результат одной команды

| Формат | Медиа ленты | Stories |
|---|---|---|
| Обычный пост | JPEG в `content/images/` | Полный JPEG в `content/reposts/` |
| Карусель | Все JPEG и соответствующие MP4 со звуком | Отдельный полный JPEG на каждый слайд |
| Reels | MP4 и финальный `-frame.jpg` в `content/reels/` | Финальный кадр целиком с подписью «Кадр из Reels» |

`content/prepared/index.json` хранит ссылки, контрольные суммы, смещение обложки и точные музыкальные кредиты. `content/reposts/index.json` хранит тот же набор источников, полный список Stories и их контрольные суммы. Сборка использует временную копию очереди, проверяет весь выбранный набор и затем сохраняет готовые файлы и реестры. В очередь одобрений результаты не записываются.

## Единая проверка перед отправкой

```text
node build-media.js <id>
node publish.js --validate-prepared <id>
node publish.js --dry-run <id>
```

Первые две команды не требуют Instagram или токена. `--validate-prepared` проверяет медиа независимо от редакционного одобрения. `--dry-run` дополнительно требует `approved`, наступившую дату и подпись, но не делает сетевых запросов и не меняет очередь.

Модуль `prepared-media.js` используется и сборщиком, и отправителем. Он сопоставляет исходный текст с сохранённым отпечатком, проверяет ссылки, локальные SHA-256, полный состав карусели и связь каждого кадра Stories с источником. Изменение текста, отсутствие финального кадра или повреждение восьмого слайда блокируют готовность.

Во время разрешённой реальной публикации тот же контроль выполняется до создания контейнера ленты. Затем проверяется содержимое публичных файлов по тем же контрольным суммам. Сборка не может проставить `approved` или подменить дату: из реестра принимаются только поля медиа. После подтверждения публикации ленты выбранные метаданные и результаты отдельных Stories сохраняются в существующей очереди.

Отдельный повтор уже начатого репоста остаётся `node publish.js --repost <id>` с прежними ограничениями неопределённого результата. Сборка не сбрасывает историю доставки.

## Локальная копия GitHub Actions

`render.yml` вызывает общий сборщик, затем `publish.js --validate-prepared`, и только после успеха сохраняет `content/images`, `content/reels`, `content/reposts`, `content/prepared` и `content/preview.html`. Новые неотслеживаемые файлы сначала добавляются в индекс Git, поэтому они не теряются при проверке изменений. Рабочая очередь не входит в коммит сборки.

Сборка, публикация ленты и самостоятельные Stories имеют общую группу `concurrency` без отмены выполняющегося процесса; checkout читает `main` после ожидания. Локальный сборщик использует ту же блокировку, что и отправитель. Расписание не менялось. Эти изменения подготовлены локально: workflow в облаке не запускался.

## Изолированная проверка

`tests/build-media.test.js` с `MEDIA_BUILD_TEST=1` создаёт копии трёх материалов в `outputs/build-integration-2026-09-11/run-*`. Изменённые ID/даты/статусы — только синтетические данные проверки. `MEDIA_CONTENT_DIR` перенаправляет сборку и валидатор в эту папку. Реальные `queue.json` и `stories.json` сравниваются побайтно до и после.

Проверяются три штатные точки входа, сборка всех восьми слайдов, MP4 Reels с аудио, метаданные, финальный кадр, валидатор и dry-run отправителя. Отдельные отрицательные случаи проверяют повреждённую Stories, отсутствующий кадр, изменённый текст и отсутствие одобрения. Итог — `integration-result.json` рядом с папкой проверки.

На этой Windows-машине для FFmpeg требуется ранее установленный Gyan FFmpeg через `FFMPEG_BIN`; CI использует свой npm-пакет `ffmpeg-static`. Браузер — установленный Edge локально и Chromium в CI. `scripts/verify-build-workflow.py` проверяет три workflow через actionlint, PyYAML и `bash -n`, не исполняя их команды.
