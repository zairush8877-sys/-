## Причина и исправление

Старый `repostToStory` отправлял исходный JPEG 1080×1350 или 1080×1920 напрямую как Stories, не подготавливая рамку и безопасные поля. Для карусели он брал только первый слайд. ID отправленной Stories отбрасывался; ошибка печаталась в журнал, а опубликованный пост уже исключался из очереди следующего запуска. Таким образом не было ни контроля полного кадра, ни надёжного списка незавершённых репостов.

Теперь `render-reposts.js` готовит JPEG 1080×1920 с тёплым светлым фоном. Изображение целиком помещается с сохранением пропорций в область x=60, y=360, ширина=960, высота=1300; подпись и номер находятся от y=300, нижний край материала — не ниже y=1660. Верхние 300 и нижние 260 пикселей не содержат важного текста. Область проверяется по фактическому размеру изображения в браузере, не только по CSS.

- Обычный пост: один полный кадр.
- Карусель: отдельная Stories на каждый слайд, порядок и количество сохраняются, номер 1/N…N/N виден. В случае видеослайдов используются подготовленные JPEG того же слайда: движение и аудио не переносятся.
- Reels: полный финальный кадр, явно подписанный «Кадр из Reels». Это анонс, а не копия всей видеозаписи или нативный кликабельный стикер репоста.

Перед будущей отправкой проверяются полный набор кадров, совпадение источников и SHA-256, размеры 1080×1920, а затем публичные JPEG по подготовленным ссылкам. Для новой публикации эта проверка встроена перед созданием контейнера ленты: отсутствие обязательных Stories или несоответствие публичных файлов останавливает весь новый выпуск заранее. Отправка исходной картинки в обход рамки больше не используется.

`build-media.js` теперь создаёт все эти кадры в штатной сборке поста, карусели или Reels. Существующие полноценные команды рендера делегируют ему работу. Ссылки, обложка и музыкальные сведения сохраняются в `content/prepared/index.json`, исходная очередь не редактируется. Сборщик и отправитель используют один модуль `prepared-media.js`; связка с `publish.js --validate-prepared` и `--dry-run` проверена на реальных локальных файлах. Подробности — [BUILD_PIPELINE.md](BUILD_PIPELINE.md).

## Учёт и повтор ошибок

`repost-state.js` хранит состояние в `post.storyRepost` внутри `content/queue.json`: ID исходного поста, отдельный статус каждого кадра, число попыток, ID контейнера, подтверждённый ID Stories и время. Существующий workflow уже сохраняет `queue.json`; дополнительный реестр доставки в другом файле не требуется.

| Состояние | Действие |
|---|---|
| `pending` / `awaiting_assets` | Доставка ещё не подтверждена; подготовить конкретный набор и проверить ссылки |
| `failed` | Сбой до `media_publish`; возможен явный повтор только этой публикации |
| `partial` | Часть слайдов подтверждена; при повторе они пропускаются |
| `published` | Все слайды имеют подтверждённые ID Stories; повтор не отправляет их снова |
| `needs_review` / `unknown` | Ответ отправки потерян либо процесс прерван: повтор запрещён до сверки с Instagram |
| `historical_unknown` | Старый учёт не содержит подтверждения; сначала сверка истории, без автоматического выпуска |

Перед вызовом `media_publish` на диск записывается `publishing`. Если ответ отсутствует или не содержит ID, нельзя считать отправку неудачной: она могла выполниться. Такая запись требует сверки в Instagram и документирования результата. При подтверждении существующей Stories в учёте необходимо сохранить её настоящий ID и источник проверки; при подтверждённом отсутствии — сохранить факт проверки перед возвратом конкретного кадра в `pending`. Это ручная операция; код не угадывает результат и не предоставляет кнопку массового сброса.

После явного разрешения выпустить конкретный материал, подготовки/размещения файлов и сверки статусов будущий оператор сможет использовать:

```text
node render-reposts.js <id>
node publish.js --repost <id> --dry-run
# Только для согласованного конкретного повтора, с токеном в окружении:
node publish.js --repost <id>
```

Обычный выпуск нового поста создаёт `pending` и вызывает новый механизм сразу после подтверждения ленты. Запуск старого уже опубликованного ID также больше не дублирует пост в ленте. Неподготовленные Stories сохраняются как требующие внимания; запуска старого хвоста здесь нет.

Локальный файл блокировки предотвращает одновременную сборку и публикацию через `build-media.js` и `publish.js` в одной папке. После аварийной остановки блокировку можно убирать только после проверки, что процесс завершён, а неопределённые отправки разобраны. В локальных копиях `render.yml`, `publish.yml` и `stories.yml` подготовлена общая группа `concurrency` без отмены выполняющегося процесса; после ожидания они получают актуальную ветку `main`. Это сериализует три вида запуска после внедрения файлов. Cron-время не менялось; изменения не отправлены в GitHub, действующие задания пока работают по прежнему коду.

Локальная блокировка не является распределённой: ручной запуск с другого компьютера она не блокирует. Также сохранность истории зависит от успешной записи статусов обратно в репозиторий. Если раннер завершился до сохранения или push отклонён, следующий выпуск надо остановить и сначала сверить Instagram и журнал попытки; старый снимок очереди не является доказательством отсутствия публикации. Абсолютная доставка «ровно один раз» при любых сбоях сети/раннера здесь не заявляется. Незавершённый репост возвращает ненулевой код завершения, сохраняя подтверждённый статус ленты, чтобы ошибка была видна оператору.
